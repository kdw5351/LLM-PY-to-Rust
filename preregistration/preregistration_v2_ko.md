## 1. 연구 질문과 가설 (가설은 제안서 그대로, 요지)

**이 연구가 다루는 상황.** "기존 Python 코드를 Rust로 이전할 때 알려진 위험이 어떻게 변하고, 남은 위험을 어떻게 줄이는가"다. "새로 개발할 때 Python과 Rust 중 무엇을 고를까"는 다루지 않는다. 산업이 AI로 Python→Rust 이전 중이다. 아는 취약점이 넘어가는가, 완화되는가, 남는 것은 왜 남는가를 센다.

**연구 질문(2026-11-13 다시 씀, 문장 고정).**
1. **RQ1 보안 변화.** Python→Rust 이전은 알려진 취약점의 잔존·제거·신규 발생에 어떤 영향을 보이며, Python→Python 재작성과 어떻게 다른가?
2. **RQ2 기존 완화.** 기존 완화 절차는 기능 시험을 통과하는 범위에서 위험을 얼마나 줄이고, 어떤 위험을 새로 만들며, 비용은 얼마인가?
3. **RQ3 잔여 실패와 추가 완화.** 기존 완화 뒤에 어떤 실패가 남으며, 그 진단을 바탕으로 만든 기법은 별도 검증 표본에서도 개선을 보이는가?

**단계·가설과의 대응.**

| 질문 | 단계 | 확증 비교 | 세부 분석(탐색·서술, 15절) |
| --- | --- | --- | --- |
| RQ1 | 1단계 | H1, H4 (H2는 사전 지정 보조) | 이전 과정에서 새로 생기거나 다른 형태로 나타나는 위험(패닉 지점·비정상 종료·unsafe·정수 지점·없는 라이브러리 이름), 고친 횟수와 보안 결과, 보이는 시험 고치기 전후(T0→T1), 데이터셋 판정과 효과 판정의 차이, 모델별 차이 |
| RQ2 | 2단계 | 2-가-1, 2-가-2, 2-나 (2-다는 사전 지정 보조) | 원 방식 그대로(기능 확인 없음)와의 차이, 선택에 쓰지 않은 기능 시험, 번역으로 사라진 위험이 되살아난 수, 호출·토큰 |
| RQ3 | 3·4단계 | 4-가, 4-나 (+ 비열등 조건) | 잔여 실패의 구성(R·N·J·T), 읽기 라벨, 정책 제공 조건과의 차이 |

- **표현 규칙.** Py→Py 대조의 결과는 "Python→Rust 이전과 Python→Python 재작성의 차이"로만 쓴다. 이 차이에는 언어 외에 모델의 언어별 숙련도, 라이브러리, 번역·수정 과정이 함께 들어 있으므로 언어만의 몫으로 쓰지 않는다. 이전 과정의 위험을 묶어 부를 때는 "이전 과정에서 새로 생기거나 다른 형태로 나타나는 위험"으로 쓴다. 그 세부 수치는 **"Rust 번역본에서 관찰하는 패닉·산술·unsafe·의존성 위험 지표"**로 쓴다. 경고 지점 수(정적 지표)와 실제로 공격할 수 있는 취약점 수(보안 시험·효과 시험으로 판정한 것)는 따로 적는다. T0→T1은 탐색이다.
- **표현 규칙(2026-11-13 세 번째 검토 반영).**
  - 모델 4종을 합친 결과는 **"선정한 네 모델을 합친 평균 결과"**로 쓴다. LLM 번역 전반에 대한 주장으로 쓰지 않는다. 모델별 방향이 갈리면 함께 적는다(12절).
  - 가설 결과의 해석은 **"가능한 해석"**으로 쓴다. 표본이 부족하거나 다른 실패 양상일 수 있다는 단서를 함께 단다. 단정하는 문장은 쓰지 않는다. 개발용 시험에서 본 양상은 "비슷한 양상을 관찰했고, 동등성은 검증하지 않았다"처럼 쓴다.
  - 신규성은 조합으로 쓴다: "Python→Rust에서 취약판·수정판 쌍과 같은 언어 재작성 대조를 두고, 기능을 확인한 번역에 고정된 공격 시험을 실행하며, 공통 받아들이기 기준 아래 완화의 효과와 부작용을 평가한다." 범위를 밝히지 않은 "그런 사례는 없다" 같은 문장은 쓰지 않는다.
  - 선행 연구 요약에서 cJSON 이식 연구(Parrillo 외)는 "알려진 CVE의 회귀 입력을 Rust 이식본에 실행했고, 남은 기능 버그와 패닉도 보고했다. 우리 연구는 여기에 취약판·수정판 쌍, 같은 언어 재작성 대조, 신규 위험 집계와 완화 비교를 둔다는 차이가 있다."로 쓴다. 공개 저장소 기준으로 옮긴 원본은 이미 패치된 cJSON 1.7.19이므로 그 CVE 시험은 옮긴 뒤 알려진 CVE가 다시 생기지 않는지(회귀 방지)를 본 것으로 적는다(모델에 준 판은 확인하지 못함). CVE 건수는 "CVE 13건(본문 기준, 표는 14/14)"로 적는다(`검토의견_반영_결정_2026-11-13.md` 11-7절)(근거: `research_notes/선행 연구 절차 대조/adjacent_exec_based.md`).
  - 근거: `검토의견_반영_결정_2026-11-13.md` 11-3·11-6·11-7절.
- 가설 H1·H2·H4의 비교 대상·표본·검정·계산은 바뀌지 않는다. 바뀐 것은 질문의 틀과 H4의 문장뿐이다.

가설 번호와 뜻은 제안서 4절 그대로다(H4의 문장만 위 표현 규칙에 맞춰 고쳐 썼고, 재는 것은 같다). 본 실험은 **옮기기(실험 A, 1단계)와 완화(실험 B, 2·4단계)** 를 하고, 그 사이에 원인 규명(3단계, 서술)을 둔다. H1·H2·H4는 옮기기 설정(Py→Rs 대 Py→Py, 같은 원본)으로 잰다.

| 단계 | 질문 | 성격 |
| --- | --- | --- |
| 1. 위협 평가 | Python의 알려진 취약점이 LLM 번역으로 Rust에 넘어가는가, 새로 생기는가 | 확증 |
| 2. 기존 완화 | 발표된 완화 기법은 얼마나 줄이고 무엇을 망가뜨리는가 | 확증 |
| 3. 원인 규명 | 가장 잘 듣는 기존 기법 뒤에도 남는 것은 무엇이고 왜 남는가 | 서술(검정 없음) |
| 4. 원인 겨냥 완화 | 그 원인을 겨냥한 기법이 남는 것을 더 줄이는가 | 확증(손대지 않은 표본 H) |

- **H1(RQ1).** 코드 실행류 결함(502·94/95·78)은 Rust로 옮기면 크게 준다. 취약판을 옮겼을 때 "없어짐"이 Py→Py(Python→Python 재작성)보다 많다. (효과 판정이 있는 종류는 효과 판정이 주 판정. H1은 정의상 효과 판정군이다. 취약 판정식은 8-4절)
- **H2(RQ1).** 검사 여부를 개발자가 정하는 결함(경로·인증·권한·정보 노출 등 논리형)은 언어와 관계없다(동등성: 차이의 판정 구간 전체가 −5%p와 +5%p 사이, 사전 지정 보조 분석 — 확증 가족 밖, 12절).
- **H4(RQ1).** 수정판을 Rust로 옮기면, 이전 과정에서 새로 생기거나 다른 형태로 나타나는 위험(패닉으로 인한 비정상 종료(248/400) 포함)이 Python→Python 재작성 때보다 많이 나타난다. 수정판을 옮겼을 때 "새로 생김"(8-4절: 단일 판정식으로 취약이 되었거나 ⑤가 새로 생긴 경우)으로 세고, Py→Rs와 Py→Py를 비교한다. 이 위험이 Rust라는 언어에만 고유하다고 주장하지 않는다.
- **H5(RQ1, 탐색).** 입력 검사·오류 처리 누락은 Rust에서 줄지만 일부는 패닉으로 형태만 바뀐다(탐색).
- **H7(RQ2·RQ3).** 완화는 남은 위험·새로 생긴 위험을 줄이면서 기능과 이미 없어진 위험을 지킨다. 2단계는 **발표된 기법을 같은 호출 상한·같은 받아들이기 기준으로** 비교하고(12절 2-가·2-나, 2-다는 보조), 4단계는 **원인을 겨냥한 새 기법이 기존 최선보다, 그리고 같은 호출 상한까지 반복한 기존 최선보다 더 줄이는지**를 손대지 않은 H에서 본다(11절). 세부는 13절 결론 규칙.
- **옛 질문과의 관계(2026-11-13, 범위 변경).** 원래 제안서는 두 언어의 직접 작성 비교를 질문에 넣었다. 이번에는 직접 작성 비교를 범위에서 빼고, 기존 코드의 이전에 집중한다. 직접 작성 조건은 더하지 않는다(배경 수치용 2개 조건도 더하지 않는다).

## 2. 데이터 · 분할

- **데이터셋:** SecCodePLT(코드 실행형 포함 다수 CWE) + CWEval(효과형 보강).
- **출발 코드 835개** = SecCodePLT 814 + CWEval 21. 원본 Python 두 판(취약·수정)이 Docker(네트워크 없음)에서 원래 결과를 재현하는 항목만(`export/reproduced_ids.txt`는 SecCodePLT 814). 주석·설명문 제거판 `export/programs_nc` 사용(835개 모두 원래 시험 결과 재현 확인).
- **분할(고정, SEED 20261112, `pipeline/make_split.py`):**
  - 개발용 100개 = `dev_touched.txt` 20(SecCodePLT) + `dev_new80.txt` 80(SecCodePLT 79, CWEval 1). 요청문·틀·받아들이기 조정에 썼다. 확증 결과에 섞지 않는다. 지금까지의 시험 운행은 모두 개발용이다.

## 4. 조건 (arm) — 조작적 정의

### 4-1. 실험 A (1단계, 옮기기)

- **Py→Rs** 와 **Py→Py**(같은 지시문, 대상 언어만 다름, 같은 실행 환경). Py→Py는 Python→Python 재작성 대조다. 결과는 "Python→Python 재작성과의 차이"로 쓰고, 언어만의 몫으로 쓰지 않는다(그 차이에 함께 들어 있는 것은 1절 표현 규칙)(우리가 대조한 세 번역 연구 SafeTrans, Chang 외, Wu 외 SoK에는 없던 대조, 사용자 결정으로 남김).
- **Py→Py 다시 생성 규칙(고정):** 유사도는 공백을 정리한 뒤 줄 단위 `difflib.SequenceMatcher` 비율이다. 0.90 이상이면 온도 0.8로 처음부터 다시 생성한다. 최대 3번. 3번 뒤에도 넘으면 그 번역을 "복사"로 표시하고 그대로 쓴다. 다시 생성한 호출은 번역 호출로 센다. 검사는 보이는 시험 고치기까지 끝난 번역(T1)에 한다. 이 규칙은 대조군에만 걸리는 선택 절차다. 그래서 ① 다시 생성된 항목 수와 "복사" 수를 보고하고, ② **다시 생성하기 전의 최초 Py→Py 결과도 저장하고 같은 판정을 한다**, ③ H1·H4를 세 가지로 낸다: 주 분석(등록 규칙대로 다시 생성한 것), 다시 생성된 항목을 뺀 것, 최초 결과를 쓴 것(뒤의 둘은 민감도). 원본과 거의 같다는 이유만으로 대조가 무효는 아니다(2026-11-13 세 번째 검토 반영).
- 출발 버전 두 가지: 취약판(남음/없어짐), 수정판(새로 생김/양쪽 안전).
- **번역 절차(SafeTrans 순서, 두 언어 같음):**
  1. **번역.** 요청문 v2(5절), 항목당 1개, temperature 0.
  2. **빌드 오류 고치기.** 최신 코드와 최신 오류만 주고 다시 받는다. **최대 5번**(SafeTrans와 같은 수).
  3. **보이는 시험으로 고치기.** 빌드된 번역에 보이는 시험(2-2절)을 돌린다. 실패하면 실패 종류(빌드 오류 / 실행 오류 / 시간 초과 / 출력 불일치)에 맞는 요청문으로 **첫 실패 시험 1개의 입력·기대 출력·실제 출력**을 주고 다시 받는다. **최대 5번.** 요청문은 SafeTrans 원문에서 "C"를 "Python"으로 바꾸고 우리 입출력 약속만 더한다. 보이는 시험이 없는 134항목은 이 단계를 건너뛴다.
- **모델이 보는 것:** 코드, 입출력 약속, 빌드 오류, 보이는 시험의 실패 1개. 판정 시험·security_policy는 보지 않는다.
- **둘 다 판정:** 3단계 직전의 번역(**T0**, 지금까지의 방식과 같음)과 3단계 뒤의 번역(**T1**). **주 분석은 T1**, T0는 민감도 분석. "시험에 맞춰 고치는 루프가 취약점을 남기는가, 없애는가"(T0→T1)는 탐색으로 두고 개수로 보고한다(15절).
- **비교 대상:** 판정용 기능 시험을 모두 통과한 번역만 보안 비교에 넣는다. 확증 비교(H1·H4·H2)는 **Py→Rs와 Py→Py가 둘 다 기능 통과한 (항목, 모델) 쌍**에서 한다. 이것이 재는 것은 "두 쪽 모두 번역에 성공한 과제에서의 보안 차이"다.
- **보조표(전체 분모):** 실용적 성과를 따로 보이기 위해, 전체 항목을 분모로 한 기능 통과 수와 "기능 통과이면서 취약하지 않은 수"를 언어별로 함께 보고한다.

- **"같은 호출 상한"의 뜻:** 조건들은 같은 호출 상한(C=6) 안에서 돈다. 실제 호출 수는 조건마다 다르다(개발용: 명세 자기 수정 약 1.2, 자기 비판 반복 약 3.1). 조건별 실제 호출·토큰을 항상 함께 보고한다.
- **모든 조건에 공통:** 같은 받아들이기 식 G*(6절). 거절되면 거절 이유를 주고 다시 시도 최대 3번, 고치는 호출은 6번까지. security_policy와 데이터셋 보안 시험은 어떤 조건에도 주지 않는다(정책 제공 참고 조건 제외). 최종 결과는 마지막으로 G*를 통과한 후보, 없으면 출발 코드(다시 번역만 예외: 처음 통과한 것이 최종).
- **원 방식 그대로의 수치(첫 결과물):** 모든 조건에서 받아들이기 기준을 거치기 전의 첫 결과물을 저장해 함께 판정한다. 추가 호출 없음. "원 방식 그대로"와 "우리 기준을 거친 것"을 나란히 보고한다(자기 비판 반복은 원래 기능 확인이 없다).
- **선택에 쓰지 않은 기능 평가(추가 호출 없음):** 번역 단계의 보이는 시험(2-2절)은 완화 단계의 받아들이기 기준에 쓰이지 않고 고치는 모델에도 보여 주지 않는다. 완화 뒤의 최종 프로그램과 첫 결과물에 이 시험을 돌려 **"완화의 선택에 쓰지 않은 기능 시험(번역 단계의 보이는 시험)에서 깨진 수"**를 조건마다 보고한다. 보이는 시험이 있는 항목에서만 잰다.
- **정책 제공 참고 조건의 지위:** 방법이 아니라 참고 조건이다. **보장된 상한이 아니다.** 정답 설명(보안 정책 글)을 주고 고치게 하는 것은 SecCodePLT 원 논문이 한 설정과 같다. 두 가지에만 쓴다: ① 3층 라벨 R·N 가르기(10절), ② 4단계의 "정책 제공 조건과의 차이"(11-5절). **완화 기법의 성적으로 보고하지 않는다.**
- **"기존 최선"을 정하는 규칙(고정):** D에서, 정책 제공 참고 조건을 뺀 조건 중 고친 뒤에도 취약한 번역이 가장 적은 조건. 같으면 호출이 적은 쪽. 모델 4종을 합쳐 센다. ② 시작 때 정하고 "변경"에 적는다: □ (② 시작 때 적어 고정). 개발용에서는 명세 자기 수정이었다.
- **뺀 조건:** 이전 문서의 조건 확인 신호 조건들(B2 검사 목록만, B3 규칙+검사 목록+점검, B4 항목별+조건 확인, B5 합친 방법, B5− 조건 신호만 뺌)은 모두 뺀다. 개발용에서 더해도 차이가 없었다: B3·B4는 B1을 못 이겼고(CPR B1 1.9 < B4 11.4 < B3 16), 새 8항목 예행에서 B5는 B1과 같았다(다르게 판정된 항목 0). 논문에는 "개발용에서 더해도 차이 없음"으로 보고한다. 규칙 𝒢 전문은 이전 문서 4절에 남고, 2단계 어떤 조건에도 쓰지 않는다.
- **뺀 추가 실행:** Py→Py 번역에 명세 자기 수정과 정책 제공 참고 조건을 돌리는 실행은 하지 않는다(사용자 결정). 우리가 대조한 세 번역 연구에는 같은 언어 대조가 없고, 이 실행은 원인 하나("언어 관련")를 가르는 데만 쓰였다.
- **조건 확인 입력(받아들이기 식 5단계에 씀, 조건 아님):** 명세에서 뽑은 검사 목록 중 **`stated`(명세가 말로 적은 것)만** 쓴다. 각 조건에 대해 정상/위반 입력 쌍(probe)을 만들어, 출발 코드가 그 조건을 이미 막는지(d0)·고친 뒤 막는지(d1) 본다. **확인 입력 요청문은 v2(`pi_probe_v2.md`)로 고정한다.** v3·v4·v5·v6은 채택하지 않았다(코드에는 남아 있고 `probe_version`을 따로 지정할 때만 켜진다). 2026-11-13 개발용 확인은 v6으로 돌렸다 — 본 실행은 v2다.
- **조건 확인 입력의 정확도(따로 보고, 방법에 되돌리지 않음):** 손대지 않은 개발용 항목에서 v2의 좋은 입력(취약 원본은 실패, 수정 원본은 통과) 수는 조건 19개 중 3, 42개 중 10, 29개 중 6이었다. 확증 실행에서도 같은 진단을 원본 두 판으로 내 보고한다.
- **넣지 않는 선행 기법과 이유:** 보안 시험을 모델에 보여 주는 방식(평가를 부풀림), Bandit 되먹임(Rust 대응 도구 없음), 검색으로 보안 지식 넣기(지식 묶음을 새로 만들어야 함), 두 비평가 방식(INDICT: 호출이 많고 원 논문이 규칙 기반 검출기로만 판정). 실행 결과 되먹임(FALCON식)과 통합 조건은 2단계의 고정 조건이 아니다 — 4단계 부품 후보로만 남는다(11절).

## 6. 받아들이기 식 G* (모든 조건 동일, 순서 고정 — 바뀌지 않음)

`pipeline/gate.py` `check()` (해시 16절, 설정 `"gate_rules":"v2"`). 후보는 아래를 **모두·이 순서로** 만족해야 받아들인다.

| 순서 | 확인 | 거절 이름 |
| --- | --- | --- |
| 1 | 빌드된다(컴파일 수정 2번까지) | build |
| 2 | **데이터셋 기능 시험(capability) 전부 통과**(func_ok) | functional_regression |
| 2b | 조건 확인 정상 입력 A0⊆A, 정상 입력 묶음 N0⊆N (보조) | functional_regression |
| 3 | 새 코드 로더·**코드 실행 크레이트**가 늘지 않음(출발 코드 대비). 그 밖의 새 의존성은 받아들이고 기록만 | loader_changed |
| 4 | **패닉 종류** clippy 위험 지점·unsafe 블록 비증가(**출발 코드 대비**). 정수 넘침·as 변환 지점은 기록만 | risk_points_increased |
| 5 | 출발 코드에서 막던 조건(d0=1)을 계속 막음 — 조건 확인 입력 v2 | security_regression |

- **기능 확인(2단계) = 전체 데이터셋 기능 시험.** 명세만 본 정상 입력으로는 기능 깨짐을 5개 중 1개만 잡았다(전역 데이터 의존 항목은 정상 입력을 못 만들고, 가장자리 입력이 안 닿음). 선행 연구 표준(보이는 시험으로 수정 받아들이고 숨긴 시험으로 평가)대로 **기능 시험을 받아들이기에 쓴다. 기능 시험은 보안 판정이 아니므로 보안 정답(보안 시험의 기대 결과)을 누설하지 않는다.** 설정 `"gate_functional":"dataset"`. 모델은 시험을 못 보고 하네스만 본다(이유 종류만 돌려줌). 받아들이기 식을 "보이는 시험"으로 바꾸지 않는다(사용자 결정, 2026-11-13). 보이는 시험은 번역 단계에서만 쓴다.
- **쓰지 않는 것:** 보안 시험·효과 시험·security_policy·공격 입력. '진전'(겨냥한 것이 나아졌는가)은 받아들이기에 넣지 않는다.
- **최종 결과(모든 조건 동일):** 마지막으로 G*를 통과한 후보, 없으면 출발 코드.
- 설정 `"gate":"unified"` 일 때만 G*를 쓴다(옛 실행은 그대로).
- 3·4단계는 규칙 v2다(2026-11-12 개발용 변경: v1에서 가장 많던 거절 사유가 보안과 무관한 의존성·정수 지점이었다).
- **이 구조의 결과(보고에 명시):** 기능 시험을 받아들이기에 쓰므로 완화 뒤 "판정용 기능 시험에서 깨진 수"는 기준이 0으로 만드는 값이다. 기능 쪽에서 실제로 잰 값은 "받아들이기 기준에서 거절된 수", "원 방식 그대로였다면 깨졌을 수"(4-2절 첫 결과물), "완화의 선택에 쓰지 않은 기능 시험(번역 단계의 보이는 시험)에서 깨진 수"(4-2절, 최종 프로그램과 첫 결과물)다.
- **기능 보존 주장의 범위:** 결론 문장은 **"받아들이기에 쓴 기능 시험을 통과하면서, 따로 숨긴 보안 시험의 실패를 줄였다."**로 제한한다. "보지 않은 입력에서도 기능을 보존한다"는 문장은 쓰지 않는다. 위 수치를 그대로 적는다.

## 9. 지표 정의

- **남음 / 없어짐 / 새로 생김**(1단계): 취약판 번역의 남음·없어짐, 수정판 번역의 새로 생김. 취약과 "새로 생김"은 8-4절 판정식으로 정한다.

- **거절 수와 이유** = 받아들이기 식에서 거절된 수(거절 이름별). **원 방식 그대로였다면 기능이 깨졌을 수** = 첫 결과물 중 판정용 기능 시험에서 깨진 수. **완화의 선택에 쓰지 않은 기능 시험(번역 단계의 보이는 시험)에서 깨진 수** = 최종 프로그램과 첫 결과물 각각, 보이는 시험이 있는 항목에서만(4-2절).
- **CPR** = 없앤 1건당 고치기 호출 수. **Cost** = 번역당 호출·토큰 수. 조건별 실제 호출·토큰은 항상 함께 낸다(같은 호출 상한이라도 실제 호출 수는 다르다). **코드 길이 변화.**
- **DoS(H4)** = ⑤칸 수.
- **정책 제공 조건과의 차이**(4단계, 11-5절).
- "기능 깨짐"은 없앤 위험으로 세지 않고 따로 센다(6절 끝의 구조 때문에 최종 후보는 기능 시험 통과 — "기능 깨짐"은 주로 출발 코드로 되돌아간 경우로 나타난다).
- 모두 **개수로 보고**(비율 아님). **보안 시험 단위와 번역 단위를 함께** 낸다. 약점 종류별, 모델별, 출처(SecCodePLT·CWEval)별.

## 11. 4단계: 원인 겨냥 완화 (만들기 D, 확증 H — 새로 더함)

### 11-2. 만들기와 고정

- **만드는 곳:** D와 개발용. D에서는 몇 번이든 고쳐 볼 수 있다. H는 보지 않는다.

### 11-3. H에서 돌리는 조건

없음, 기존 최선, **기존 최선 반복**(4-나의 대조), 새 기법, 정책 제공 참고 조건. 없음·기존 최선·정책 제공 참고 조건은 ①에서 이미 만든 것을 쓴다. 기존 최선 반복은 새 기법의 호출 상한이 ④에서 정해진 뒤 ⑤에서 만든다.
- **기존 최선 반복의 정의:** 기존 최선을 직전 결과에서 다시 시작해, 새 기법의 호출 상한에 닿을 때까지 반복한다. 호출 상한은 신호를 만드는 호출까지 모두 센 값이다.

### 11-4. 확증 비교: H (2026-11-13 검토 반영, 둘로 둠)

- **4-가.** 새 기법 대 기존 최선: 취약판 출발 번역 중 고친 뒤에도 취약한 수(번역 단위 짝 비교, 12절 주 검정).
- **4-나.** 새 기법 대 기존 최선 반복(11-3절): 같은 단위·같은 검정.
- **4-비열등(판정 순서의 조건):** 수정판 출발 번역의 새로 생긴 비율 차이 d_신규(새 기법 − 기존 최선)의 판정 구간 **상한이 +5%p보다 작으면** 비열등 성립. 하한이 +5%p보다 크면 여유를 넘는 악화, 구간이 +5%p에 걸치면 판단 불가(13-2절 세 갈래).
- 결론은 13-2절의 판정 순서 일곱 줄 가운데 처음 맞는 줄 하나로 쓴다. "원인을 겨냥한 부품이 호출을 더 쓴 것 이상의 효과를 냈다"는 문장은 4-나가 성립할 때만 쓴다. 4-가만 성립하면 "새 절차 전체가 기존 절차보다 낫다"까지만 쓴다.

### 11-5. 정책 제공 조건과의 차이 (보고 지표)

정책 제공 참고 조건은 정답 설명을 준 조건이라 방법이 아니고, 보장된 상한도 아니다. 세 수 — 기존 최선 뒤, 새 기법 뒤, 정책 제공 조건 뒤에 남은 번역 수 — 를 그대로 낸다. 정책 제공 조건이 기존 최선보다 적게 남기면, 새 기법이 그 차이 가운데 몇 개를 메웠는지("차이를 메운 수")를 개수로 함께 낸다(예: 기존 최선 뒤 70개, 정책 제공 조건 뒤 30개, 새 기법 뒤 50개이면 40개 중 20개). 두 가지 특별한 경우:
- 정책 제공 조건이 기존 최선보다 적게 남기지 못했으면 "차이를 메운 수"는 계산하지 않고 그렇게 적는다.
- 새 기법이 정책 제공 조건보다 적게 남기면 그 사실을 그대로 적는다.

### 11-6. 보조 비교 (탐색)

겨냥한 라벨에 속한 번역에서의 효과(⑥ 뒤 H에도 3단계의 1~3층을 그대로 적용해 라벨을 붙인다), 약점 종류별·모델별. (새 기법 대 기존 최선 반복은 확증 4-나로 올렸다.)

### 11-7. 남은 것이 너무 적을 때의 규칙 (고정)

D에서 기존 최선 뒤 남은 번역이 모델 4종을 합쳐 **40개 미만**이면 4단계 확증을 하지 않는다. 결과에는 **"사전 지정한 잔여 건수 기준에 따라 추가 기법의 확증을 진행하지 않았다."**고 쓰고, 남는 수의 상한을 함께 보고한다. 이때 ③~⑤는 하지 않고, ⑥에서 H의 1·2단계만 평가한다. 확증 가족에서 4-가·4-나가 빠지고 Holm은 5개에 건다(12절).

- **허용 여유 5%p의 근거(검정력과 분리).** 5%p는 "이보다 작은 차이는 실무에서 구분할 가치가 작다"고 미리 정한 값이다. 탐지할 수 있어서 고른 값이 아니다. 신규 위험 쪽에서는 5%p가 느슨할 수 있다. 그래서 d_신규 구간의 상한 값을 항상 함께 보고하고, 더 엄격한 여유 2%p로 본 결과(세 갈래)를 보조로 낸다. 판정 순서(13-2절)는 5%p로만 정한다.
- **비열등·동등성:** 동등성은 TOST(양쪽, 여유 δ). 비열등은 한쪽(상한만, 여유 δ).
- **군집 표준오차:** Miller 2411.00640, 시드 대리 묶음 기준.
- **분석 스크립트:** ① 전에 고정하고 해시를 적는다(4단계 부분은 ④에서 덧붙임). 해시: □ (16절).
- **잔여(확증 전 완료):** 개발용 강화 결과로 실제 ICC·분산을 재서 위 비교별 검정력 모의실험의 가정 값으로 넣는다.

## 13. 결론 규칙

질문은 "제안 방법이 이기는가"가 아니라 **"같은 받아들이기 기준·같은 호출 상한에서 어떤 기법(과 부품)이 효과를 내는가"**다. 어느 쪽 결과도 결론이 되도록 미리 적는다. 기능에 관한 문장은 6절 끝의 범위("받아들이기에 쓴 기능 시험을 통과하면서, 따로 숨긴 보안 시험의 실패를 줄였다.")를 넘지 않는다.

### 13-1. 2단계 (735개, ⑥ 뒤)

- **2-가.** 명세 자기 수정이 없음과 다시 번역 둘 다보다 고친 뒤에도 취약한 수가 적으면(Holm 보정 뒤 유의): **"같은 호출 상한에서, 명세 자기 수정은 명세 없이 다시 번역만 한 것보다 고친 뒤에도 취약한 번역이 적었다."** 고 쓴다(조건별 실제 호출·토큰과 함께). 다시 번역과만 차이가 없으면 그렇게 쓴다.
- **2-나.** 명세 자기 수정이 일반 보안 지시보다 적으면(Holm 보정 뒤 유의): **"같은 수정 절차에서 명세를 주면 더 줄어든다."** 고 쓴다. 반대면 반대로 쓴다.
- **보조(명세 자기 수정 대 자기 비판 반복):** **"명세 자기 수정 절차가 자기 비판 반복 절차보다 …였다"** 로 쓴다(절차끼리의 비교. 명세의 몫으로 쓰지 않는다).
- **2-다(사전 지정 보조, 동등성).** 두 번 대 한 번의 차이의 판정 구간 전체가 −5%p와 +5%p 사이에 있으면: **"두 번 한 것과 한 번 한 것의 차이는 사전 지정한 ±5%p 범위 안이었다."** 고 쓴다(호출 수와 함께). 아니면 "사전 지정한 ±5%p 범위 안에 든다고 보이지 못했다"고 쓴다.
- 차이도 동등성도 못 보인 비교는 "가리지 못했다"고 쓴다.
- 조건마다 원 방식 그대로(첫 결과물)의 수치를 함께 내고, 기능 확인 없는 평가와의 차이를 개수로 쓴다.
- 정책 제공 참고 조건의 수치는 기법의 성적으로 쓰지 않는다.

### 13-2. 4단계 (H, ⑥ 뒤) — 판정 순서 (2026-11-13 세 번째 검토 반영, 이전의 결합 판정표 다섯 줄을 대체)

**용어.**
- d_잔여 = (새 기법 뒤 취약 번역 비율) − (기존 최선 뒤 취약 번역 비율). 음수면 개선.
- d_신규 = (새 기법의 새로 생긴 비율) − (기존 최선의 새로 생긴 비율). 양수면 악화.
- 구간은 12절의 판정 구간(BCa의 명목 95% 구간).
- **신규 위험이 두 조건 모두 0건인 경우(12절 예외 가).** 구간으로 판정할 수 없어 신규 위험은 "판정 보류"가 된다. 비열등 성립이 조건인 3·4·6줄에는 들어가지 않는다. 4-가가 유의한 개선이면 5줄이 되고, 문장 뒤에 "신규 위험은 두 조건 모두 0건이었다(번역 N개, 묶음 F개). 구간으로 판정할 수 없어 보류했다."를 덧붙인다. 희귀 사건에서도 판정하려면 묶음 크기와 번역 단위 추정 대상을 반영한 상한 계산법을 따로 정당화해야 하며, **정함(2026-11-15): 따로 만들지 않는다. 보류 규칙대로 한다.**

**신규 위험의 세 갈래(먼저 정한다).**
- 비열등 성립: d_신규 구간의 **상한 < +5%p**.
- 여유를 넘는 악화: d_신규 구간의 **하한 > +5%p**.
- 판단 불가: 구간이 +5%p에 걸침.

**동등성**은 d_잔여 구간 전체가 −5%p와 +5%p 사이에 있는 것이다. 비열등과 다른 판정이다.

**판정 순서(위에서부터, 처음 맞는 줄 하나를 고른다).**

| 순서 | 조건 | 쓰는 문장 |
| --- | --- | --- |
| 1 | 신규 위험이 "여유를 넘는 악화" | **"새 기법은 신규 위험을 허용 여유 5%p 넘게 늘렸다."** (잔여 결과는 수치로만 덧붙인다) |
| 2 | 4-가에서 새 기법이 유의하게 더 많이 남김 | **"새 기법은 기존 최선보다 남는 것이 많았다."** |
| 3 | 4-가 유의한 개선, 4-나 유의한 개선, 신규 위험 비열등 성립 | **"원인을 겨냥한 기법은 기존 최선보다, 그리고 같은 호출 상한까지 반복한 기존 최선보다 남는 것을 더 줄였다. 측정한 신규 위험 증가는 허용 여유 5%p 이내였다."** |
| 4 | 4-가 유의한 개선, 신규 위험 비열등 성립, 4-나는 유의하지 않음 | **"새 절차 전체는 기존 최선보다 남는 것을 더 줄였다. 호출을 더 쓴 효과와 구분되지는 않았다."** |
| 5 | 4-가 유의한 개선, 신규 위험은 판단 불가 | **"새 기법은 남는 것을 더 줄였다. 신규 위험이 허용 여유 안인지는 가리지 못했다."** |
| 6 | 4-가 유의하지 않음, d_잔여 동등성 성립, 신규 위험 비열등 성립 | **"추가 기법의 차이는 사전 지정한 ±5%p 범위 안이었고, 측정한 신규 위험 증가는 허용 여유 5%p 이내였다."**(CPR·Cost와 함께) |
| 7 | 그 밖 | **"가리지 못했다."**(어느 부분을 가리지 못했는지 적는다) |

- **겹침.** 3~5줄에서 d_잔여의 구간이 ±5%p 안에도 들면(동등성도 성립), 그 줄의 문장 뒤에 "개선의 크기는 사전 지정한 ±5%p 범위 안이었다"를 덧붙인다(작지만 정밀하게 잰 개선).
- 유의는 Holm 보정 뒤. d_신규 구간의 상한 값을 어느 경우에나 함께 적는다. 여유 2%p로 본 세 갈래는 보조로 함께 낸다(12절).
- 정책 제공 조건과의 차이(11-5절)를 어느 경우에나 함께 낸다.
- 4단계의 비교는 3절의 모델 집합 규칙(4단계 조건이 모두 있는 모델만)으로 한다.
- "원인을 겨냥한 부품이 호출을 더 쓴 것 이상의 효과를 냈다"는 문장은 4-나가 성립할 때(3줄)만 쓴다. 4-가만 성립하면 "새 절차 전체가 기존 절차보다 낫다"까지만 쓴다.
- 11-7절 규칙이 걸리면 4단계 결론 대신 **"사전 지정한 잔여 건수 기준에 따라 추가 기법의 확증을 진행하지 않았다."**와 남는 수의 상한을 쓴다.

### 13-3. 공통

- 효과 틀 있는 종류는 효과 판정으로, 없는 종류는 데이터셋 판정으로 — **두 묶음 나눠** 보고한다. 확증 검정은 8-4절 단일 판정식으로 한 번 한다.
- 합친 결과의 문장은 "선정한 네 모델을 합친 평균 결과"로 쓴다(1절 표현 규칙). 효과 판정군에서 "위험 기능이 제거됐다"는 8-5절의 "위험 기능 제거"로 분류된 것에만 쓰고, 그 밖은 "고정된 공격 묶음에서 효과가 관찰되지 않았다"로 쓴다.
- 2-가가 성립하면 기능에 관한 문장은 **"받아들이기에 쓴 기능 시험을 통과하면서, 따로 숨긴 보안 시험의 실패를 줄였다."**로 쓰고, "완화의 선택에 쓰지 않은 기능 시험에서 깨진 수"를 그대로 적는다. "보지 않은 입력에서도 기능을 보존한다"는 문장은 쓰지 않는다.
- **공정·중립 — 개발용 참고값(Haiku, 이미 쓴 69항목, 대상 130개 = 취약판 번역 64 + 수정판 번역 66, 본 결과 아님):** 기능 지키며 없앤 보안 시험(108개 중) 명세 자기 수정 91, 두 번 93, 자기 비판 반복 39(기준 없이 원 방식 그대로면 61이지만 130개 중 43개에서 기능이 깨지고 수정판 번역 8개에 새로 생김). 고친 뒤에도 취약한 번역(54개 중) 11·11·39. 명세 자기 수정 대 두 번은 갈린 번역 0개(남은 11개가 같은 집합, 호출은 두 배). 확증에서 같은 결과가 나오면 그대로 보고한다. 비용(Cost·CPR)도 함께 낸다.
