# 실험 설계서: 위협 평가 → 기존 완화 → 원인 규명 → 원인 겨냥 완화 (2026-11-13)

**지위:** 본 실험(API 2종 + A100 2종) 전에 고정하는 설계. 교수님 승인과 사전 등록 최종본의 바탕이 된다. 지금까지의 사전 등록(`사전등록_2026-11-12.md`)에서 바뀌는 곳은 12절에 모았다.
**목표:** 추가 실험 없이 논문이 서도록, 네 단계의 질문·표본·조건·판정·분석·결론 규칙을 미리 정한다.
**한 줄:** 남들의 C→Rust 연구를 Python→Rust로 옮겨, 기존 Python 코드를 Rust로 이전할 때 알려진 위험이 어떻게 변하는지 실행으로 재고(RQ1), 발표된 완화 기법을 같은 기준으로 평가하고(RQ2), 그래도 남는 취약점의 원인을 조건을 바꿔 가려낸 뒤 그 원인을 겨냥한 기법을 손대지 않은 표본에서 검증한다(RQ3).
**무게 중심(2026-11-13 검토 반영):** 1·2단계가 본체, 3단계는 설명, 4단계는 추가 검증이다. 4단계가 유의하지 않아도 논문이 서도록 쓴다. 1·2단계에서 기존 이해를 바꿀 수 있는 비교를 앞에 둔다: 데이터셋 판정과 효과 판정의 차이, Python→Python 재작성과의 차이(Py→Py 대조. 이 차이에는 언어 외에 모델의 언어별 숙련도, 라이브러리, 번역·수정 과정이 함께 들어 있으므로 언어만의 몫으로 쓰지 않는다), 보이는 시험 고치기가 보안 결과를 바꾸는지(T0→T1, 탐색), 기능 확인 없는 평가와의 차이(첫 결과물).

## 0. 연구 질문과 네 단계

**이 연구가 다루는 상황.** "기존 Python 코드를 Rust로 이전할 때 알려진 위험이 어떻게 변하고, 남은 위험을 어떻게 줄이는가"다. "새로 개발할 때 Python과 Rust 중 무엇을 고를까"는 다루지 않는다.

**연구 질문(2026-11-13 다시 씀, 문장 고정, `검토의견_반영_결정_2026-11-13.md` 10절).**
1. **RQ1 보안 변화.** Python→Rust 이전은 알려진 취약점의 잔존·제거·신규 발생에 어떤 영향을 보이며, Python→Python 재작성과 어떻게 다른가?
2. **RQ2 기존 완화.** 기존 완화 절차는 기능 시험을 통과하는 범위에서 위험을 얼마나 줄이고, 어떤 위험을 새로 만들며, 비용은 얼마인가?
3. **RQ3 잔여 실패와 추가 완화.** 기존 완화 뒤에 어떤 실패가 남으며, 그 진단을 바탕으로 만든 기법은 별도 검증 표본에서도 개선을 보이는가?

**범위.** 같은 명세로 두 언어를 직접 작성해 비교하는 것은 이번 범위에서 뺀다. 이유: ① 이 연구의 중심 상황(기존 코드의 이전)과 다른 상황이다. ② 지금 데이터의 과제 설명은 Python을 전제로 쓰여 있어 두 언어의 직접 작성을 공정하게 비교하기 어렵다. 원래 제안서는 직접 작성 비교를 질문에 넣었으므로 이것은 제안서에 대한 범위 변경이다. 후속 연구로 적는다. 직접 작성 조건은 더하지 않는다.

| 단계 | 답하는 질문 | 질문 | 산출 | 성격 |
| --- | --- | --- | --- | --- |
| 1. 위협 평가 | RQ1(확증 H1·H4, 보조 H2) | Python의 알려진 취약점이 LLM 번역으로 Rust에 넘어가는가, 새로 생기는가 | 남음·없어짐·새로 생김의 개수(약점 종류별, 모델별), Py→Py 대조와의 차이 | 확증 |
| 2. 기존 완화 | RQ2(확증 2-가-1·2-가-2·2-나, 보조 2-다) | 발표된 완화 기법은 얼마나 줄이고 무엇을 망가뜨리는가 | 조건별 고친 수·새로 생긴 수·거절 수·호출 수, "기능 확인 없는 평가"와의 차이 | 확증 |
| 3. 원인 규명 | RQ3(앞부분: 무엇이 남는가) | 가장 잘 듣는 기존 기법 뒤에도 남는 것은 무엇이고 왜 남는가 | 원인 × 약점 종류 × 모델 표, 분류 일치도 | 서술(검정 없음) |
| 4. 원인 겨냥 완화 | RQ3(뒷부분: 별도 검증 표본에서의 개선, 확증 4-가·4-나) | 그 원인을 겨냥한 기법이 남는 것을 더 줄이는가 | 새 기법 대 기존 최선, 새 기법 대 기존 최선 반복(같은 호출 상한)의 짝 비교 | 확증(손대지 않은 표본), 추가 검증 |

- 세부 분석(탐색·서술)과 질문의 대응은 사전 등록 1절 표와 15절. RQ1에서 이전 과정의 위험을 묶어 부를 때는 "이전 과정에서 새로 생기거나 다른 형태로 나타나는 위험"으로 쓰고, 세부 수치(패닉 지점·정수 지점·unsafe·없는 라이브러리 이름)는 "Rust 번역본에서 관찰하는 패닉·산술·unsafe·의존성 위험 지표"로 쓴다. 경고 지점 수와 실제로 공격할 수 있는 취약점 수는 따로 적는다. 비정상 종료(⑤)는 판정으로 센다.
- **표현 규칙(2026-11-13 세 번째 검토 반영, 사전 등록 1절과 같음).** Py→Py 대조는 "Python→Rust 이전과 Python→Python 재작성의 차이"로만 쓴다. 모델 4종을 합친 결과는 "선정한 네 모델을 합친 평균 결과"로 쓴다. 가설 결과의 해석은 "가능한 해석"으로 쓰고, 표본 부족이나 다른 실패 양상일 수 있다는 단서를 단다. 신규성은 조합으로 쓴다: "Python→Rust에서 취약판·수정판 쌍과 같은 언어 재작성 대조를 두고, 기능을 확인한 번역에 고정된 공격 시험을 실행하며, 공통 받아들이기 기준 아래 완화의 효과와 부작용을 평가한다." cJSON 이식 연구(Parrillo 외)는 "알려진 CVE의 회귀 입력을 Rust 이식본에 실행했고, 남은 기능 버그와 패닉도 보고했다. 우리 연구는 여기에 취약판·수정판 쌍, 같은 언어 재작성 대조, 신규 위험 집계와 완화 비교를 둔다는 차이가 있다."로 쓴다. 공개 저장소 기준으로 옮긴 원본은 이미 패치된 cJSON 1.7.19이므로 그 CVE 시험은 옮긴 뒤 알려진 CVE가 다시 생기지 않는지(회귀 방지)를 본 것으로 적는다(모델에 준 판은 확인하지 못함). CVE 건수는 "CVE 13건(본문 기준, 표는 14/14)"로 적는다(`검토의견_반영_결정_2026-11-13.md` 11-7절).

## 1. 표본

**항목.** SecCodePLT 814 + CWEval 21 = 835개. 원본 Python 두 판(취약·수정)이 격리 실행에서 원래 결과를 재현한 것만.

| 묶음 | 항목 | 시드 묶음 | 쓰임 |
| --- | --- | --- | --- |
| 개발용 | 100 | — | 도구·요청문 만들기. 100개 모두 사용(마지막 CWEval 1개는 2026-11-14 도구 점검에 씀) |
| 새 개발용(보안 시험 없음) | 149 | — | 도구가 끝까지 도는지 확인 |
| **확증용 D (원인 규명용)** | **285** | 133 | 1·2단계의 일부, 3단계 전부, 4단계 기법 만들기 |
| **확증용 H (최종 검증용)** | **450** | 204 | 1·2단계의 일부, **4단계 확증** |
| 실제 저장소 사례(PatchEval 함수 단위) | 7 → 약 10 | — | 바깥 타당성, 서술만 |

- **D와 H를 나누는 규칙(고정):** 확증용 735개를 시드 묶음 단위로, 약점 종류별 층을 지켜 4 대 6에 가깝게 나눴다. 시드 20261113, `pipeline/make_split_dh.py`(f9038d264915568f), 목록 `split_dh_2026-11-13/`(D fda99450b56ab69f, H 5e78b42659545b9f). 결과를 보지 않고 정했다.
- **왜 나누나.** 4단계 기법은 3단계에서 본 "남는 것"을 보고 만든다. 같은 항목으로 그 기법을 평가하면 결과 맞추기가 된다. 그래서 만드는 데는 D만 쓰고, 평가는 H에서만 한다.
- **1·2단계는 735개 전체로 결론을 낸다.** 조건과 분석을 지금 고정하므로 D를 먼저 봐도 결론 규칙이 바뀌지 않는다.
- 한계: 정규식(1333) 31개는 시드 묶음이 하나라 모두 H에 들어갔다. D에는 이 종류가 없다.
- 보이는 시험이 있는 항목: D 285개 중 233, H 450개 중 368.
- **CWEval 20개(D 10, H 10)는 1단계에만 들어간다.** 이 항목들에는 과제 설명 글이 없어서 명세를 쓰는 조건(명세 자기 수정, 정책 제공 참고 조건)과 받아들이기 기준 준비를 돌릴 수 없다(도구를 맞추다 확인, 2026-11-13). 따라서 2·3·4단계의 표본은 SecCodePLT 715개(D 275, H 440)다. 번역·판정·효과 판정은 CWEval에도 돈다.

| 차례 | 하는 일 | 대상 | 평가(보안 시험 실행) |

- ⑤에서 일부 모델을 못 쓸 때: 4단계의 모든 비교(4-가, 4-나, 신규 위험)는 4단계 조건이 모두 있는 모델만 합쳐서 한다. "기존 최선"은 ②에서 네 모델로 정한 것을 그대로 쓴다. 1·2단계 분석에는 빠진 모델의 결과를 그대로 넣고, 4단계와 같은 모델 집합으로 본 2단계 결과를 민감도로 함께 낸다.
- 모델 순서: GPT-4o → Sonnet → Qwen 32B → Qwen 14B. 번역하는 모델과 고치는 모델은 같다. 하위 에이전트 대리 실행은 본 실험에 쓰지 않는다.

## 3. 1단계: 위협 평가 (실험 A)

- **조건:** Py→Rs와 Py→Py(같은 지시문, 대상 언어만 다름, 같은 실행 환경). 출발 판 둘(취약판, 수정판).
- **Py→Py 다시 생성 규칙:** 공백을 정리한 뒤 줄 단위 `difflib.SequenceMatcher` 비율이 0.90 이상이면 온도 0.8로 처음부터 다시 생성, 최대 3번. 3번 뒤에도 넘으면 "복사"로 표시하고 그대로 쓴다. 다시 생성한 호출은 번역 호출로 센다. 검사는 보이는 시험 고치기까지 끝난 번역에 한다. 대조군에만 걸리는 선택 절차이므로 다시 생성된 항목 수와 "복사" 수를 보고한다. 다시 생성하기 전의 최초 Py→Py 결과도 저장하고 같은 판정을 한다. H1·H4는 세 가지로 낸다: 주 분석(등록 규칙대로 다시 생성한 것), 다시 생성된 항목을 뺀 것, 최초 결과를 쓴 것. 원본과 거의 같다는 이유만으로 대조가 무효는 아니다.
- **번역 절차(SafeTrans 순서):** 번역 → 빌드 오류 고치기(최대 5번) → 보이는 시험으로 고치기(최대 5번, 첫 실패 시험의 입력·기대·실제 출력). 보이는 시험은 SecCodePLT+ 시험 중 취약판·수정판 원본이 같은 결과를 내는 입력만. 판정 시험(데이터셋의 기능·보안 시험)은 모델에 보여 주지 않는다.
- **둘 다 판정:** 보이는 시험 고치기 전(T0)과 후(T1). 주 분석은 T1, T0는 민감도 분석. T0→T1 비교는 탐색이다.
- **표본:** 항목·조건당 1개(temperature 0). 무작위 100항목은 5개씩 더(temperature 0.8) 만들어 흔들림을 본다.
- **비교 대상:** 판정용 기능 시험을 모두 통과한 번역만. 확증 비교는 **Py→Rs와 Py→Py가 둘 다 기능 통과한 (항목, 모델) 쌍**에서 한다. 이것이 재는 것은 "두 쪽 모두 번역에 성공한 과제에서의 보안 차이"다. 보조로, 전체 항목을 분모로 한 기능 통과 수와 "기능 통과이면서 취약하지 않은 수"를 언어별로 함께 보고한다.
- **판정:** 데이터셋 판정 + 효과 판정(502·94·95·22·78. 이 가운데 코드 실행류는 502·94·95·78), 다섯 칸 분류. 사전 등록 8절 그대로. 취약 판정식은 7절(단일).
- **가설(지금 사전 등록 그대로, RQ1):** H1(코드 실행류는 Rust에서 준다, Py→Py 대비), H2(논리형은 언어와 무관, 동등성: 차이의 판정 구간 전체가 −5%p와 +5%p 사이, 사전 지정 보조), H4(수정판을 옮길 때 이전 과정에서 새로 생기거나 다른 형태로 나타나는 위험 — 새로 취약해진 수와 비정상 종료 — 가 Py→Py보다 많다).
- **보고:** 취약판 번역의 남음·없어짐, 수정판 번역의 새로 생김. 보안 시험 단위와 번역 단위 둘 다. 약점 종류별, 모델별, 개수.

## 4. 2단계: 기존 완화 기법 (실험 B)

- **겹침.** 3~5줄에서 d_잔여의 구간이 ±5%p 안에도 들면, 그 줄의 문장 뒤에 "개선의 크기는 사전 지정한 ±5%p 범위 안이었다"를 덧붙인다(작지만 정밀하게 잰 개선).
- d_신규 구간의 상한 값을 어느 경우에나 함께 적고, 여유 2%p로 본 세 갈래를 보조로 낸다. 4단계의 비교는 2절의 모델 집합 규칙을 따른다.
- "원인을 겨냥한 부품이 호출을 더 쓴 것 이상의 효과를 냈다"는 문장은 4-나가 성립할 때(3줄)만 쓴다. 4-가만 성립하면 "새 절차 전체가 기존 절차보다 낫다"까지만 쓴다.
- **정책 제공 조건과의 차이(보고 지표):** 정책 제공 참고 조건은 정답 설명을 준 조건이라 방법이 아니고 보장된 상한도 아니다. 세 수(기존 최선 뒤, 새 기법 뒤, 정책 제공 조건 뒤에 남은 번역 수)를 그대로 낸다. 정책 제공 조건이 기존 최선보다 적게 남기면 새 기법이 그 차이 가운데 몇 개를 메웠는지 개수로 함께 낸다(예: 기존 최선 뒤 70개, 정책 제공 조건 뒤 30개, 새 기법 뒤 50개이면 40개 중 20개). 정책 제공 조건이 기존 최선보다 적게 남기지 못했으면 "차이를 메운 수"는 계산하지 않고 그렇게 적는다. 새 기법이 정책 제공 조건보다 적게 남기면 그 사실을 그대로 적는다.
- **보조 비교:** 겨냥한 라벨에 속한 번역에서의 효과(H에도 3단계의 1~3층을 그대로 적용해 라벨을 붙인다), 약점 종류별·모델별. (새 기법 대 기존 최선 반복은 확증 4-나로 올렸다.)
- **검정력 어림(Haiku 개발용 비율로 계산, 사전 등록 12절의 비교별 검정력 모의실험으로 대체하고 D 결과로 다시 계산한다):** H 450항목에서 모델 하나당 취약판 번역 약 420개가 기능 통과, 그중 약 350개가 번역 뒤에도 취약, 기존 최선 뒤 약 70개가 남는다. 새 기법이 그중 15%(약 10개)를 더 고치고 망가뜨리는 것이 1개 이하면 모델 하나에서도 짝 검정으로 가려진다. 모델에 따라 남는 수가 달라지므로 이 수치는 계획용이다.

## 7. 판정·지표·통계 (공통)

- 판정, 다섯 칸 분류, 효과 판정의 범위: 사전 등록 8·14절 그대로.
- 지표는 모두 개수로 낸다. 보안 시험 단위와 번역 단위를 함께 낸다.
- **취약 판정식(단일).** 번역 하나가 "취약"이다 ⇔ 그 번역의 보안 사례 중 하나라도 다음에 해당한다: 효과 판정이 있는 종류(502·94·95·22·78)는 효과가 실제로 발생(④칸), 그 밖의 종류는 데이터셋 판정이 "뚫림". 효과 판정군의 ③(받아들였지만 효과 없음)과 ⑤(비정상 종료만)는 주 판정에서 취약으로 세지 않고 칸별 개수로 따로 보고한다. 민감도 분석: 모든 종류를 데이터셋 판정으로 본 결과를 함께 낸다. **"새로 생김"**(H4와 수정판 출발 비교): 수정판 출발 번역에서 위 식으로 취약이 되었거나, 비정상 종료(⑤)가 새로 생긴 경우.
- **효과가 없다는 판정의 해석(③칸, 2026-11-13 세 번째 검토 반영, 사전 등록 8-5절).** 결론은 "고정된 공격 묶음에서 효과가 관찰되지 않았다"(관찰)와 "위험 기능이 제거됐다"(해석)로 나눠 쓴다. 뒤의 문장은 ㉡가 "없다"인 것에만 쓴다. 결과를 본 뒤 공격 입력을 보강하지 않는다. ③칸 전수 확인 기준(사람이 한다, 결과 보기 전에 고정):

| 물음 | 답 |
| --- | --- |
| ㉠ 공격 입력이 해당 처리 경로까지 갔는가 | 갔다 / 그 전에 거절됐다 / 알 수 없다 |
| ㉡ 위험 기능이 번역본에 있는가 | 없다(위험 기능 제거) / 있다(그 공격 표현만 듣지 않음) / 알 수 없다 |
| ㉢ 요구한 기능은 유지됐는가 | 기능 시험 결과(기계적) |

- 표시는 "위험 기능 제거"(㉡ 없다), "공격 표현만 실패"(㉡ 있다), "구분 불가"(그 밖). 세 수를 따로 보고한다. 주 결과에서는 "구분 불가"와 "공격 표현만 실패"도 "사라짐"으로 세되 그 수를 항상 옆에 적는다. 민감도: 이 둘을 "남음"으로 본 결과를 함께 낸다. 도구는 ③칸 사례 목록(항목, 모델, 조건, 기능 시험 결과, 종료 방식)을 뽑아 주기만 하고, 분류는 사람이 한다.
- 효과 판정군과 데이터셋 판정군은 나눠 보고하되, 확증 검정은 위 단일 판정식으로 합쳐서 한 번 한다(H1만 정의상 효과 판정군).
- **주 검정(하나):** 시드 묶음 단위 치환 검정(모델 4종 합, 양측, 10,000번; 한 묶음의 모든 번역·모든 모델의 두 조건 라벨을 함께 맞바꿈). 결과는 "선정한 네 모델을 합친 평균 결과"로 쓴다. 동등성(차이의 판정 구간 전체가 −5%p와 +5%p 사이)과 비열등(d_신규 판정 구간의 상한 < +5%p)은 따로 판정한다. 모델별 정확 McNemar와 모델별 수치는 보조로 모두 보고하고, 방향이 갈리면 적는다. 독립 가정과 묶음 보정을 둘 다 보고.
- **구간 계산법(분석 동결 전에 정한다, 사전 등록 12절).** 모의 확인에서 묶음 단위 백분위 재표본 구간은 0을 빼는 비율이 4.5~8.7%였다. 실제 묶음 구조와 비교별 표본 크기에서 네 방법(백분위 재표본, BCa, 재표본-t, 묶음 강건 표준오차 + t 분포)의 포함률을 모의로 재고, 90% 구간의 실제 포함률이 89% 이상이면서 90%에 가장 가까운 방법을 고른다. **모의 결과(2026-11-13, `dataset_pilot/_sims/`):** 명목 90% 구간의 실제 포함률은 백분위 재표본 87.3~91.2%(평균 88.6), BCa 83.5~89.7%(87.1), 재표본-t 79.7~90.0%(87.4), 묶음 강건 표준오차 + t 87.4~90.5%(88.8)였다. 네 방법 모두 "모든 칸에서 89% 이상"을 채우지 못했다. 모두 조금씩 느슨하고 비열등 판정에 불리한 방향으로 벗어난다. 묶음 강건 + t의 명목 95% 구간은 실제 포함률 93.0~95.5%였다. **경계 오판율 확인(2026-11-14, 기준은 돌리기 전에 고정):** 참 차이가 판정 경계(±5%p)일 때 잘못 "범위 안"이라고 한 비율이 모든 칸에서 6.0% 이하인 것은 BCa(최대 4.3%)와 재표본-t(최대 3.8%)의 명목 95% 구간뿐이었다. 이전 후보(묶음 강건 + t의 명목 95%)는 최대 6.7%로 채우지 못했다. **고른 방법(2026-11-14 고정): BCa의 명목 95% 구간.** 실제로 쓰는 비교 넷(H2, 2-다, 4단계 남는 위험, 4단계 신규 위험)에서 경계 오판율은 2.6~4.3%였고, 예외 처리 규칙(모든 차이가 0인 경우, 엇갈린 묶음이 1~4개인 경우, 계산이 안 되는 경우)을 미리 정했다. "모든 상황에서 검증된 95% 구간"이라고 쓰지 않는다. 전체 결과와 규칙은 사전 등록 12절. 분석 스크립트의 기본값은 정해질 때까지 백분위 재표본이다.
- **표본 크기.** 전체 735개 하나로 낸 최소 탐지 차이를 모든 가설의 근거로 쓰지 않는다. 비교마다 실제로 들어가는 항목·시드 묶음 구조·개발용 비율(가정)·Holm 7개 보정을 넣은 검정력 모의실험으로, 검정력 80%로 잡을 수 있는 차이를 비교별로 낸다(4단계 것은 D 결과로 다시 계산). **모의 결과(2026-11-13, 가장 엄격한 보정 α÷7 기준, 전체 표와 가정은 사전 등록 12절):** H1 11.0%p(코드 실행류 135항목·60묶음, 기준 비율 가정에 따라 13.3%p), H4 1.2%p, 2-가-1 0.7%p 이하, 2-가-2 4.0%p, 2-나 3.9%p, 4-가 4.7%p, 4-나 4.6%p. 개발용 비율을 가정한 이 모의에서는 2·4단계 비교가 5%p 차이를 잡았다(보장이 아니다). 2-가-1 값은 "완화가 취약하지 않던 번역을 취약하게 만들지 않는다"는 가정에서 나온 것이고, 그 가정을 풀면 0.8~1.4%p다. **H1은 8~13%p보다 작은 차이를 잡지 못한다.** H1에서 유의하지 않으면 "차이가 없다"가 아니라 "이 크기의 표본으로 가리지 못했다"로 쓴다. H2·2-다·4-비열등은 구간 너비로 내며 구간 계산법이 정해진 뒤 채운다(□). 효과 판정 승인 수가 적은 종류(CWEval의 경로 2개, 명령 주입 1개)는 종류별 일반화를 하지 않는다.
- **허용 여유 5%p의 근거.** "이보다 작은 차이는 실무에서 구분할 가치가 작다"고 미리 정한 값이며, 탐지할 수 있어서 고른 값이 아니다. 신규 위험 쪽에서는 느슨할 수 있으므로 구간의 상한 값을 항상 함께 보고하고, 여유 2%p로 본 결과를 보조로 낸다.

## 부록 가. 원인 분류 절차의 개발용 시험 (Haiku, 기존 69항목)

**지위:** 절차를 시험한 것이다. 11개는 작고, 이미 쓴 항목이고, 본 모델이 아니다. 여기서 나온 원인의 구성을 결과로 쓰지 않는다. Py→Py 쪽 완화 실행이 없어 "언어 관련"은 판별하지 못했다. 이 부록은 당시 기록이라 옛 라벨(I·C·G·B)과 "오라클"이라는 이름을 그대로 둔다. 새 이름: I→R, C→N, G→J, B→T, 오라클→정책 제공 참고 조건(5절).

**대상:** 명세 자기 수정 뒤에도 취약한 번역 11개(두 번 해도 같은 11개 → "예산"으로 풀린 것 0).

**1·2층(기계적).** 고친 답이 모두 거절됨 3개(셋 다 권한 863, 거절 이유는 기능 시험 실패), 받아들여졌는데 남음 8개. 실패한 보안 시험 17개의 방식: 거절해야 하는데 받아들임 6, 값이 다름 7, 값을 기대했는데 오류 2, 출력 형식 깨짐 2(둘 다 취약판 원본도 같은 식으로 깨지는 자원·정규식 종류).

**3층(오라클 실행: 정답 설명을 주고 같은 130개를 다시 고침).** 오라클은 보안 시험 108개 중 99개를 없앴고(명세 자기 수정 91), 고친 뒤 취약한 번역은 54개 중 7개, 새로 생긴 것 0, 호출 144번.

**4층(읽기, 분류자 2명).** 명세 쪽(S)은 11개 모두 일치(κ 1.0): 구체적 1, 값·규칙 없음 4, 정책 글에만 있음 6. 코드 쪽(K)은 8개 일치(κ 0.55).

**이 시험에서 배운 것(본 실험 절차에 반영)**
1. **읽기만으로는 "정보 부족"을 과대평가한다.** 읽기로는 11개 중 10개가 "명세에 구체적으로 없음"이었지만, 실제로 정답 설명을 줘서 고쳐진 것은 5개뿐이다. 명세에 없다고 분류된 것 중 5개는 알려 줘도 못 고쳤다. 그래서 원인은 3층(조건을 바꿔 돌린 결과)으로 정하고, 4층은 설명으로만 쓴다.
2. **"기능과 충돌"은 독립된 원인이 아닐 수 있다.** 여기서는 모두 정보 부족의 결과였다(규칙을 몰라 짐작으로 넣은 검사가 정상 동작까지 막음). 본 실험에서는 G를 I·C와 겹쳐 세고 겹침을 표로 낸다.
3. **코드 쪽 분류(K)는 판단 규칙이 더 필요하다.** 순서를 정해 고쳤다(원인분류 절차의 변경 참고).
4. **"판정이 엄격한 것"이 실제로 있다.** 11개 중 1개는 걸러서 값을 돌려주길 기대한 시험에 거절로 답한 경우다(두 분류자 모두 K4). 따로 세는 규칙이 필요하다는 근거다.
5. 오라클도 생성의 우연을 탄다. 명세 자기 수정은 고쳤는데 오라클은 못 고친 번역이 1개 있었다. 본 실험에서는 I·C 판별에 이 흔들림이 섞이므로, 100항목 추가 표본으로 흔들림의 크기를 함께 보고한다.

**4단계에 주는 뜻(방향만).** 이 구성이 본 모델에서도 비슷하다면, 겨냥할 것은 둘이다. ① 정보 부족 가운데 "명세가 조건을 말하지만 규칙이 없는" 경우(여기서는 권한 3개): 기능 시험과 맞는 해석을 찾게 하는 부품. ② 구현 한계: 실행 근거를 되먹이는 부품. "정책 글에만 있는" 조건은 모델에 준 정보로는 알 수 없으므로 겨냥하지 않고 정책 제공 참고 조건과의 차이로 보고한다. (뒤에 6절 표에 "빠진 보안 조건을 스스로 찾기" 부품이 더해졌다 — 변경 참고.)
