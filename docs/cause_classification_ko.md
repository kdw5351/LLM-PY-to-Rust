# 남은 취약점의 원인 분류: 절차와 분류표 (2026-11-13)

**지위:** 절차. 항목을 열어 보기 **전에** 고정한다. 오늘은 개발용 69항목(Haiku)의 남은 것으로 이 절차를 한 번 돌려 절차 자체를 시험한다. 시험에서 분류표를 고쳐야 하면 "변경"에 적고, 본 실험에는 고친 판을 쓴다.
**대상:** 완화(명세 자기 수정)를 거친 뒤에도 보안 시험이 실패하는 번역("남은 것"). 본 실험에서는 "기존 최선" 뒤에도 사전 등록 8-4절의 단일 취약 판정식으로 취약한 번역이다(2026-11-13 검토 반영).
**원칙:** 읽어서 짐작하기 전에, **조건을 바꿔 돌려 본 결과**로 원인을 가른다. 읽기 분류는 그다음이고, 두 명이 따로 분류해 일치도를 낸다. 공격 입력은 새로 만들지 않는다. 보고는 라벨과 개수만 한다.

## 1. 1층: 기록에서 기계적으로 나오는 것 (사람 판단 없음)

| 라벨 | 뜻 | 근거 |
| --- | --- | --- |
| P1 고친 답이 모두 거절됨 | 모델은 고치려 했으나 받아들이기 기준이 모두 거절해 출발 코드로 돌아감 | 실행 상태(거절 이유: 기능 시험 실패 / 위험 지점 증가 / 막던 입력을 못 막음 / 빌드 실패) |
| P2 받아들여졌으나 여전히 취약 | 고친 답이 기준을 통과했는데 보안 시험이 실패 | 실행 상태 + 판정 |

## 2. 2층: 실패 방식 (실행 결과에서 기계적으로)
실패한 보안 시험마다, 기대한 결과와 실제 결과의 종류를 비교한다.

| 라벨 | 뜻 |
| --- | --- |
| F1 거절해야 하는데 받아들임 | 기대는 오류(거절), 실제는 값을 돌려줌 |
| F2 값이 다름 | 기대도 실제도 값인데 서로 다름(예: 걸러 내야 할 것을 그대로 돌려줌) |
| F6 값을 기대했는데 오류 | 기대는 값(걸러서 돌려줌), 실제는 오류(거절). "판정이 엄격한 것"일 수 있다 |
| F4 자원·시간 | 시간 초과, 메모리 초과 |
| F5 비정상 종료 | 패닉, 신호로 죽음, 출력 형식 깨짐 |

## 3. 3층: 조건을 바꿔 돌려 가르는 라벨

라벨은 **관찰한 사실의 이름**이다. 해석(가설)은 따로 적는다(2026-11-13 검토 반영, 이전 이름 I·C·G·B). "정책 제공 참고 조건"은 명세와 보안 정책 글을 함께 주는 완화 조건이다(코드 이름 `oracle`, 이전 이름 "오라클"). 보장된 상한이 아니다.

| 라벨 | 뜻(관찰) | 해석(가설) | 필요한 실행 |
| --- | --- | --- | --- |
| **R 정책 제공에 반응** | 기존 최선 뒤에는 남고, 보안 정책 글을 준 조건에서는 고쳐짐 | 정보 부족 | 정책 제공 참고 조건 |
| **N 정책 제공 뒤에도 남음** | 보안 정책 글을 줘도 남음 | 구현 한계 | 정책 제공 참고 조건 |
| **J 기능 시험 거절과 연관** | 고친 답이 기능 시험 때문에 거절됨(1층 P1 중 기능 시험 실패). 정책 제공 조건에서도 같으면 그렇게 적는다 | 기능과의 충돌 | 실행 상태 + 정책 제공 참고 조건 |
| **L 언어 관련** | 같은 완화를 Py→Py 번역에 하면 고쳐지고 Py→Rs에서는 남음(또는 그 반대) | — | Py→Py 번역에 같은 완화(본 실험에서는 하지 않음 → 판별 안 함) |
| **T 반복에 반응** | 같은 조건을 한 번 더 하면 고쳐짐 | 예산 | 두 번 조건 |

한 번역이 여러 라벨에 걸릴 수 있다(예: R이면서 J). 표에는 겹침을 그대로 센다. Py→Py 완화 실행이 없으므로 L은 "판별 못 함"으로 둔다.

**생성 흔들림:** R의 개수 옆에 반대 방향(기존 최선은 고쳤는데 정책 제공 조건은 못 고친 수)을 적는다. 이 수가 R에 섞인 우연의 크기를 가늠하게 한다.

## 4. 4층: 읽어서 붙이는 라벨 (두 명이 따로)
3층에서 R·N·J로 갈린 것에 이유를 붙인다. 분류자는 명세 글(모델에 준 것), 보안 정책 글(모델에 주지 않은 정답 설명), 고친 뒤의 코드, 2층 라벨을 본다.

**S: 명세가 그 조건을 말하는가**
- S1 구체적으로 말함(무엇을, 어떤 값·목록으로 막을지 적혀 있음)
- S2 말하지만 값·범위가 없음(예: "크기를 제한한다"만 있고 상한이 없음)
- S3 명세에는 없고 보안 정책 글에만 있음
- S4 어디에도 없음(보안 시험만 요구함)

**K: 고친 뒤 코드의 상태**
- K1 해당 검사가 없음
- K2 검사가 있으나 불완전(일부 경우만 막음, 경계가 다름, 순서가 틀림)
- K3 검사가 있고 맞아 보임(판정 방식이나 기대 형식의 차이가 의심됨)
- K4 다른 방식으로 막음(기대한 것은 거절인데 걸러서 처리하는 등)

**분류 규칙**
- 분류자 2명은 서로의 답을 보지 않는다. 같은 지시문, 같은 자료.
- 일치도: S와 K 각각 일치한 개수와 κ를 낸다.
- 불일치는 연구자가 근거를 보고 정한다. 정한 이유를 한 줄로 남긴다.
- 본 실험에서는 일치한 것 중 무작위 30개를 연구자가 다시 확인해 틀린 개수를 보고한다.
- K3과 K4는 "취약점이 남았다"가 아니라 "판정이 엄격하다"일 수 있으므로(코드는 막는데 시험이 기대한 형태와 다름) 따로 세고, 주 결과에서 빼고도 계산해 함께 보고한다.

## 5. 보고 형식
- 3층 라벨 × 약점 종류 표, 라벨 × 모델 표. 개수. R 옆에 반대 방향 수.
- 4층의 S × K 표. 개수와 일치도.
- "R이면서 S1"처럼 층끼리 어긋나는 칸은 따로 적는다(명세에 있는데 정답 설명을 줘야만 고친 경우).
- 4단계 부품을 고르는 20% 규칙은 새 라벨(R·N·J·T)의 개수로 적용한다(사전 등록 11-1절).
